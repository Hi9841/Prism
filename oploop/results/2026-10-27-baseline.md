## J5: search correctness

Method: OCR of the settled frame of each query, 8 frames for each app (2 in each session). Then a person examined each reported difference on the side-by-side PNGs `raw/20261027-005435/frames/pair-qNN.png` (GPUI left).

**Result: the two apps show the same result rows.**
This is true for all 13 queries.
The sections, the row titles, the subtitles, the order, and the selected row are equal.

Only one reported difference is real (below). The other OCR differences have three causes:

- OCR errors, for example `CLAUDEmd` and `WINDOV`.
- Text boxes that OCR split in a different way, for example the path and "Drag to copy".
- Lines that OCR did not read in one of the two frames.

Verified differences:

1. **Truncation of long text (presentation, not search).** Tauri ends a cut title or path with "…" (CSS `text-overflow: ellipsis`). GPUI cuts the text at the edge with no ellipsis. Examples:
   - `HyperType-snippets.json`: GPUI `HyperType-snippets.example.jsc` (the title runs to the path column, with no gap). Tauri `HyperType-snippets.example.j…`.
   - `HyperType-snippets.json`: GPUI path `C:\Users\hi\Desktop\Work\HyperType\Hy`. Tauri `C:\Users\hi\Desktop\Work\HyperType\…`.
   - `crhome`: GPUI `chrome_chrome_Unpacker_Beg` touches the path. Tauri `chrome_chrome_Unpacker_…`.
   - `notepad`: GPUI path `C:\Program Files\IDA Free 9.3\docs\user-g`. Tauri `C:\Program Files\IDA Free 9.3\docs\user…`.

Changes that are not app differences:

- `crhome`, the sixth file row: the folder name changes between runs in the two apps (`chrome_chrome_Unpacker_BeginUn…`, `chrome_chrome_url_fetcher_<n>`). These are temporary Chrome folders in the live catalog.
- Each app read the same text in all its own frames for 12 of 13 queries (`crhome`: 2/8 for each app, for the reason above).

## Other observations

### Foreground

On the bench activation path, the Tauri palette took the foreground in 20/20 opens. The GPUI palette took it in 0/20 opens.
The bench process does not have the foreground when it sends the signal (GPUI: `SetEvent`, Tauri: `WM_COPYDATA`).
Typed keys still arrive, because the bench posts them to the window.

A user who opens Prism with a second launch can see this difference: the GPUI palette can show with no keyboard focus.
Before you call it a defect, do a check with a real second launch (for example from the Start menu).

### Startup

- **Startup work.** In the first 60 s after a start, the Tauri tree used 20.3 s CPU and GPUI used 11.6 s. Readiness (less than 3% CPU for 3 s) came after 21-33 s for GPUI and 24-117 s for Tauri.

## What the bench cannot measure

- **Display latency.** `PrintWindow` gives the frame that DWM has. It does not give the time when the monitor shows it. The two apps go through the same DWM, so the comparison stays fair.
- **Resolution.** One capture takes about 7 ms. Each time has an error of up to 7 ms. A difference of less than about 7 ms between two medians is not significant.
- **Real keyboard path.** The bench posts `WM_CHAR` to the window. It does not go through the keyboard driver, the raw input path, or the Win-key hook. J2 does not measure the Win-key path, because the bench must not send global input.
- **Per-character typing.** The bench posts each query as one burst. A real user types with gaps between the keys.
- **Exact row text for GPUI.** GPUI has no accessibility tree and no row trace in release builds. J5 uses OCR and a person's check. A small text difference that OCR cannot read and a person does not see can stay hidden.
- **A quiet machine.** Other agents used the CPU and wrote files during the runs. The block order and the per-session medians show the effect: the session drift is less than 8 ms for J2 and less than 15 ms for J3.
