Image Thumbnail Decoding on Indexed File Search Results

src-tauri/src/files.rs:523–568
Evidence
Static code path confirmed
Normal UI Limit
Up to 8 results
Disposition
Implemented lazy thumbnails

Confirmed issue (fixed): Before the change, files.rs indexed_file_entry invoked image_thumbnail(path) for each selected indexed result. The command already ran inside spawn_blocking, so this was search-result latency and worker I/O, not a direct WebView UI-thread stall. The helper caps the input file at 32 MiB, but decoded memory can exceed the compressed file size. The normal frontend request asks for 8 results, not 20.

Before (Synchronous Decode per Search Hit)
fn indexed_file_entry(entry: &SearchEntry) -> Option<FileEntry> { let path = Path::new(entry.path.as_ref()); - let metadata = std::fs::metadata(path).ok()?; let name = path.file_name()?.to_string_lossy().into_owned(); Some(FileEntry { name, path: entry.path.to_string(), parent: path.parent().map(|v| v.to_string_lossy().into_owned()).unwrap_or_default(), - is_directory: metadata.is_dir(), - thumbnail: (!metadata.is_dir()) - .then(|| image_thumbnail(path)) - .flatten(), }) } // Decodes up to 32MB JPEG/PNG/WebP per hit synchronously! fn image_thumbnail(path: &Path) -> Option<String> { let image = image::ImageReader::open(path).ok()?.with_guessed_format().ok()?.decode().ok()?; let preview = image.thumbnail(64, 64); ... }
Implemented (Lazy Thumbnail, Preserved Stale-Path Check)
fn indexed_file_entry(entry: &SearchEntry) -> Option<FileEntry> { let path = Path::new(entry.path.as_ref()); let metadata = std::fs::metadata(path).ok()?; // Preserve deleted-entry behavior let name = path.file_name()?.to_string_lossy().into_owned(); Some(FileEntry { name, path: entry.path.to_string(), parent: path.parent().map(|v| v.to_string_lossy().into_owned()).unwrap_or_default(), + is_directory: metadata.is_dir(), + thumbnail: None, // Filled by get_file_thumbnail for image rows }) }
Pros & Performance Gains
  • Removes image decode and PNG/base64 work from ordinary indexed search responses.
  • Preserves the existing stale-entry contract while allowing a separate visible-row thumbnail request.
  • Measure search latency and decoded allocations on representative image sets before assigning a priority.
Trade-offs
  • Inline previews need a lazy, cancellable IPC path and a cache; removing thumbnails outright changes the UI.
PRISM-PERF-02 P2 · Medium (situational) Logic & V8 Engine

Math Parser False Positives for Digit-Bearing App Queries

src/lib/math.ts:219–224
Parser Behavior
Caught and returned null
Timing
Not measured
Disposition
Implemented with gate tests

Confirmed issue: The previous isMathLike gate treated any digit-bearing alphanumeric query as calculator input, so names such as vlc3, 7zip, and word2016 could reach tryEvaluate. The parser catches malformed input and returns null; this was unnecessary work, not an unhandled exception. The gate now recognizes literals, operators, parser functions/constants, and supported Unicode operators, with regression tests for the app-name cases.

Before (Permissive Regex Matches Normal App Searches)
export function isMathLike(input: string): boolean { const s = input.trim().toLowerCase(); if (s.length === 0 || s.length > 120) return false; - if (!/\d/.test(s)) return false; - return /^[\d\s.+\-*/^%()a-z]+$/.test(s); // 'vlc3' has \d and matches [a-z0-9] -> returns TRUE! // '7zip' has \d and matches [a-z0-9] -> returns TRUE! }
Implemented (Strict Gate, Preserved Parser Tokens)
+ const hasOperator = /[+\-*/^%()]/; + const knownMathToken = /\b(?:sqrt|abs|floor|ceil|round|ln|log|sin|cos|tan|asin|acos|atan|exp|pi|e|tau)\b/; + const isLiteral = /^\d+(?:\.\d+)?$/; export function isMathLike(input: string): boolean { const s = input.trim().toLowerCase().replace(/×/g, "*").replace(/÷/g, "/"); if (s.length === 0 || s.length > 120) return false; + // Keep bare numeric results; reject ordinary digit-bearing names. + if (!/^[\d\s.+\-*/^%()a-z]+$/.test(s)) return false; + if (!/\d/.test(s) && !knownMathToken.test(s)) return false; + if (!hasOperator.test(s) && !isLiteral.test(s) && !knownMathToken.test(s)) return false; + if (/[a-z]/.test(s) && !knownMathToken.test(s)) return false; + return true; }
Pros & Performance Gains
  • Reduces false-positive parser attempts for ordinary app and file names.
  • Retains bare numbers and supported operator/function expressions.
  • Measure parser attempts and input latency in WebView2 before claiming a performance gain.
Trade-offs
  • Guard logic must share the parser's normalization rules, including constants and any supported Unicode operators.

Invariant Query Normalization Inside the App Scoring Loop

src/lib/search.ts:108–160
Evidence
One call per candidate today
Timing

Disposition
Implemented reuse

Confirmed issue (fixed): In fuzzyApps, normalizeText(lowerQuery) was invariant across the candidate loop. The function already normalized the query once to compute significantLength; the fix reuses that exact value rather than adding a second normalization. The candidate count and timing are data-dependent and require profiling.

Before (normalizeText Called in Every Iteration)
export function fuzzyApps(apps: AppEntry[], query: string, limit = 8, opts = {}): AppEntry[] { ... for (const app of pool) { - const score = appScore(app, lower, tokens); if (score !== null && score >= minimumScore) results.push({ item: app, score }); } } function appScore(app: AppEntry, lowerQuery: string, tokens: string[]): number | null { - if (app.normalizedName && normalizeText(lowerQuery) === app.normalizedName) { return 100; } ... }
Implemented (Reuse Existing Pre-Computation)
export function fuzzyApps(apps: AppEntry[], query: string, limit = 8, opts = {}): AppEntry[] { ... + const normalizedQuery = normalizeText(lower); + const significantLength = normalizedQuery.length; for (const app of pool) { + const score = appScore(app, lower, tokens, normalizedQuery); if (score !== null && score >= minimumScore) results.push({ item: app, score }); } } + function appScore(app: AppEntry, lowerQuery: string, tokens: string[], normalizedQuery: string): number | null { + if (app.normalizedName && normalizedQuery === app.normalizedName) { return 100; }
Pros & Performance Gains
  • Removes repeated query-string allocation from the exact-match branch.
  • Small, low-risk improvement on the per-keystroke path.
  • Benchmark with representative app counts before assigning a larger priority.
Trade-offs
  • Keep the normalized value and its length derived from one source to avoid duplicating work.
PRISM-NATIVE-01 P1 · High UI Thread Blocking

Slow Taskbar Settings IPC Work on the Blocking Command Path

src-tauri/src/lib.rs:1037–1090
Evidence
Blocking commands confirmed
Slow Work Scope
Registry, files, PNG decode
Disposition
Implemented async offload

Confirmed issue (fixed): Before the change, these non-async Tauri commands ran on the blocking IPC path. get_taskbar_settings reads registry values and preview files; select_custom_start_icon and set_taskbar_start_icon can read and decode PNG data; remove_custom_start_icon performs filesystem/settings work but does not decode a PNG on every call. The code path could delay the window while the operation ran, but no 15–45 ms or dropped-frame measurement is present.

Before (Sync Commands Blocking Main UI Thread)
#[tauri::command] fn get_taskbar_settings(app: tauri::AppHandle) -> Result<taskbar_customization::TaskbarSettings, String> { // Synchronously reads registry + reads up to 12 PNG files from disk! taskbar_customization::settings(&app) } #[tauri::command] fn select_custom_start_icon(app: tauri::AppHandle, id: String) -> Result<(), String> { // Synchronously reads file and runs PNG decoder on main thread! taskbar_customization::select_custom_start_icon(&app, &id) }
Implemented (Offload Slow Variants)
// Apply this async + spawn_blocking shape to get, select, set, and remove. #[tauri::command] async fn get_taskbar_settings(app: tauri::AppHandle) -> Result<taskbar_customization::TaskbarSettings, String> { tauri::async_runtime::spawn_blocking(move || taskbar_customization::settings(&app)) .await .map_err(|e| format!("settings task failed: {e}"))? } #[tauri::command] async fn select_custom_start_icon(app: tauri::AppHandle, id: String) -> Result<(), String> { tauri::async_runtime::spawn_blocking(move || { taskbar_customization::select_custom_start_icon(&app, &id) }) .await .map_err(|e| format!("custom icon task failed: {e}"))? }
Pros & Performance Gains
  • Moves filesystem, registry, and decode work off the command/UI thread.
  • Measure command duration and frame timing on slow and redirected drives after the change.
Trade-offs
  • The operation still consumes worker time and has completion latency; async dispatch does not make it zero-cost.
PRISM-FE-01 P3 · Low React Rendering

Inline Row Callbacks Prevent ResultRow React.memo from Skipping Work

src/features/palette/Palette.tsx:665–694
Evidence
Inline callback confirmed
Scope
One prop among many
Disposition
Implemented callback contract

Confirmed issue (fixed): renderResultRow previously passed a fresh onRemoveHistory closure for every row. That prop alone prevented React.memo(ResultRow) from skipping a row when the parent rendered. The IIFE is incidental, other callbacks can also change identity, and the resulting render cost has not been profiled.

Before (Fresh Closures Generated on Every Render)
function renderResultRow(item: PaletteItem, index: number, reorderable: boolean, removable: boolean) { return ( <ResultRow key={item.id} item={item} index={index} selected={palette.selected === index} removable={removable} - onRemoveHistory={() => app.removeHistory(item.id)} onSelect={palette.select} ... /> ); }
Implemented (Correct Callback Contract)
function renderResultRow(item: PaletteItem, index: number, reorderable: boolean, removable: boolean) { return ( <ResultRow key={item.id} item={item} index={index} selected={palette.selected === index} removable={removable} + onRemoveHistory={app.removeHistory} onSelect={palette.select} ... /> ); }
Pros & Performance Gains
  • Removes one avoidable fresh function prop from each row.
  • ResultRow now accepts an item id and calls onRemoveHistory(item.id) inside each remove-button handler.
  • Profile render counts before claiming that all row reconciliation is eliminated.
Trade-offs
  • The current prop type is () => void; changing it to (id: string) => void requires updating both remove buttons.
PRISM-NATIVE-02 P2 · Medium Vectorization

Per-Pixel Buffer Copy in Taskbar Icon Overlay

src-tauri/src/taskbar_icon_overlay.rs:51–53
Static Cost
9,216 pixels at 96×96
Timing
Not measured
Disposition
Implemented buffer cleanup

Confirmed issue (fixed): write_icon_file previously copied a 96×96 RGBA buffer through a per-pixel loop. pixels.as_raw() exposes the contiguous subpixel buffer, but the compiler may already optimize the loop. The old capacity expression also multiplied the raw buffer length by four, over-reserving memory.

Before (Per-Pixel Iterator Loop)
fn write_icon_file(path: &Path, pixels: &RgbaImage) -> Result<(), String> { ... let mut bytes = Vec::with_capacity(ICON_MAGIC.len() + 8 + pixels.len() * 4); bytes.extend_from_slice(ICON_MAGIC); bytes.extend_from_slice(&pixels.width().to_le_bytes()); bytes.extend_from_slice(&pixels.height().to_le_bytes()); - for pixel in pixels.pixels() { - bytes.extend_from_slice(&pixel.0); - } ... }
Implemented (Contiguous Copy and Correct Capacity)
fn write_icon_file(path: &Path, pixels: &RgbaImage) -> Result<(), String> { ... let raw_pixels = pixels.as_raw(); let mut bytes = Vec::with_capacity(ICON_MAGIC.len() + 8 + raw_pixels.len()); bytes.extend_from_slice(ICON_MAGIC); bytes.extend_from_slice(&pixels.width().to_le_bytes()); bytes.extend_from_slice(&pixels.height().to_le_bytes()); + bytes.extend_from_slice(raw_pixels); ... }
Pros & Performance Gains
  • Uses the image crate's contiguous raw buffer and avoids over-reserving capacity.
  • Output remains byte-for-byte identical; benchmark this infrequent settings operation before prioritizing it.
Trade-offs
  • Rust and allocator behavior should be measured in release builds; no instruction-count claim is justified.
