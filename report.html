Primary bug: switching Window material breaks the corners

Symptom. In Settings → Appearance → Window material, switching between Acrylic / Mica / Solid damages the rounded corners of the launcher window: the native material shows through the corners as a hard-edged or wrongly-rounded sheet that clashes with the shell's rounded silhouette.

Root cause chain

  1. The rounded look is CSS-only. The native window is square. The main window is configured with transparent: true, decorations: false, shadow: false. src-tauri/tauri.conf.json (main window) Neither tao 0.35.3 nor any Prism code ever sets DWMWA_WINDOW_CORNER_PREFERENCE (verified by grepping the tao crate sources and all of src-tauri/src - there are zero DwmSetWindowAttribute calls in the repo). The corners look round only because .shell clips the webview with border-radius: 24px 24px 8px 8px over a transparent webview. src/styles/tokens.css - .shell
  2. Switching material writes a DWM system backdrop across the full rectangular HWND. set_window_style → apply_window_look → window.set_effects(...) ends up in window-vibrancy 0.6.0, which on Windows 11 sets DWMWA_SYSTEMBACKDROP_TYPE: acrylic → DWMSBT_TRANSIENTWINDOW, mica → DWMSBT_MAINWINDOW, solid → DWMSBT_DISABLE. src-tauri/src/lib.rs:754 apply_window_look · ~/.cargo/.../window-vibrancy-0.6.0/src/windows.rs
  3. DWM clips the backdrop sheet with its own radius (~8px), not the CSS radii. Once a backdrop is active, the material paints the entire square window rectangle, clipped only by the system's default corner policy. Every pixel outside the CSS-rounded shell stays transparent in the webview, so the raw material becomes visible in the corners. Result: two mismatched rounding curves stacked (CSS 24px top vs DWM ~8px), which reads as "broken corners". In Solid mode the backdrop is off, transparency hides everything outside the shell, and the illusion works - which is exactly why only the switch breaks it.
  4. The code that tries to control the native radius is dead on Windows. EffectsBuilder::new().effect(effect).radius(12.0).color(tint) looks like it aligns the native corner radius, but tauri's Windows vibrancy implementation destructures only { effects, color } from the config. radius is applied on macOS only. src-tauri/src/lib.rs:764-769 · ~/.cargo/.../tauri-2.11.5/src/vibrancy/windows.rs (apply_effects signature)
  5. The fallback ladder can select a material with no corner clipping at all. Acrylic falls back to Mica then to Effect::Blur. Blur uses SetWindowCompositionAttribute(ACCENT_ENABLE_ACRYLICBLURBEHIND), which has no DWM corner treatment whatsoever: a perfectly square blur sheet behind a rounded CSS shell. src-tauri/src/lib.rs:773-787 · window-vibrancy windows.rs apply_blur
  6. The switch happens live while the window is visible. Each change runs clear + apply (clear_effects calls clear_blur, clear_acrylic and clear_mica in sequence), so the user watches the backdrop toggle, flicker, and repaint stale corner pixels until WebView2 catches up. tauri-2.11.5/src/vibrancy/windows.rs clear_effects
Root cause in one sentence: the app never claims rounded corners natively (DWMWA_WINDOW_CORNER_PREFERENCE is never set), so any DWM backdrop material paints into the square window corners that the CSS-only design assumes stay transparent, while the one API call meant to align radii (.radius(12.0)) is silently ignored on Windows.

Recommended fix

Claim the corners natively and match the radii. In apply_window_look (or once at window setup), after applying effects:

// src-tauri/src/lib.rs - after set_effects succeeds
use windows::Win32::Graphics::Dwm::{DwmSetWindowAttribute, DWMWA_WINDOW_CORNER_PREFERENCE};
use windows::Win32::UI::Controls::DWMWCP_ROUND;

let pref: u32 = DWMWCP_ROUND.0;   // Win11 standard ~8px round corners
unsafe {
    DwmSetWindowAttribute(
        HWND(hwnd.0),
        DWMWA_WINDOW_CORNER_PREFERENCE,
        &pref as *const _ as _,
        4,
    );
}
  • Match the CSS radius to the DWM radius when a backdrop is active. With a backdrop on, DWM rounds at ~8px, so .shell should use 8px corners under [data-surface="glass"]; keep the current generous 24px/8px only for solid mode if that silhouette is preferred. Two matching curves = clean corners.
  • Delete or comment .radius(12.0) as macOS-only so nobody trusts it again.
  • Consider dropping Effect::Blur from the fallback ladder on Win11 (backdrop is supported there), since SWCA blur both looks wrong at corners and has known lag artifacts.
  • Optional polish: briefly hide or fade the window during material switches to avoid the visible backdrop toggle flicker.
  • Verify manually: switch Acrylic → Mica → Solid → Acrylic with the palette open; corners should stay a single consistent curve, including on light theme and after a webview refresh.
